# Codex: отдельный автор и сборка видео

Языки генерации: русский `ru`, каракалпакский `kaa`, узбекский `uz` (латиница). Для всех используется одна настроенная модель Google TTS и голос Puck; сценарий, подписи и речь следуют выбранному языку. После озвучки и проверки длительности 3D-сборка продолжается автоматически. Прежняя ручная проверка языка удалена из основного процесса; старые ожидающие записи продолжаются при запуске приложения после проверки владельца и разрешений. Готовые и неудавшиеся задания не перезапускаются автоматически.

Телеметрия генерации: брокер передаёт этапы создания, проверки, доработки, сборки и проверки файла. Во время сборки он читает свежие числовые контрольные точки доверенного рендерера; основной сервер сохраняет их вместе с уроком. Общий процент и оставшееся время приблизительны, этапы LLM не имитируют продвижение по таймеру. Ошибки передаются фиксированными кодами и безопасными названиями этапов, без частных журналов и ключей. Повторный запуск очищает ошибку, готовая озвучка используется по прежним правилам кэша.

Для отдельного обновления брокера можно задать `AI_TEACHER_BROKER_VERSION`, для автора — `AI_TEACHER_AUTHOR_VERSION`; `AI_TEACHER_WORKER_VERSION` остаётся общим значением по умолчанию и фиксирует рендерер. Обновлять приложение и брокер следует после завершения активных заданий. Текущая доработка интерфейса и телеметрии не изменяет модель, голос или 3D-движок.

Основной сайт хранит документы, сценарии, задания и готовые MP4. Динамический код урока выполняется в отдельных контейнерах. Брокер доступен только в сети `author_control`, требует отдельный Bearer-токен и не публикует порт на хосте.

- Брокер: доверенный Node.js и Docker CLI, единственная очередь заданий. Только он получает Docker socket. Основная база `/opt/ai-teacher/data` не монтируется в worker.
- Автор: Codex CLI **0.163.0**, `gpt-6-astra` / `ultra`, отдельная серверная авторизация в каталоге `AI_TEACHER_CODEX_AUTH` из `authoring.env` (по умолчанию `/opt/ai-teacher/codex-auth`), единственный каталог задания `/job`. Команды Codex используют `workspace-write` с отключённой сетью инструментов.
- Проверка и рендер: отдельный контейнер без сети, авторизации, Docker socket и базы. Chromium, FFmpeg, Three.js, GSAP, Playwright Core. Для текущего production-выпуска выбран профиль 8 CPU / 6 ГБ, 256 процессов, корневая файловая система только для чтения. Доверенный параметр брокера `WORKER_RENDER_CPUS` допускает значения от 1 до 8, значение по умолчанию в коде и Compose — 6; память фиксирована на 6 ГБ. Автор ограничен 4 ГБ / 2 CPU. Образ Mesa llvmpipe уже развёрнут и проверен коротким серверным примером; полный 600-секундный рендер отменён пользователем и не готов.
- Сценарий проходит самостоятельную проверку автором. Код проверяется кадрами; автор получает результаты и может исправить его дважды. Готовность выставляется после проверки рендера и SHA256 MP4.

Ключи OpenAI и Google не передаются рендереру. Сохранённый вход настольного Codex не копируется. Для сервера выполняется отдельный вход. Неинтерактивный `codex exec` и режимы ограничений описаны в [официальной документации OpenAI](https://learn.chatgpt.com/docs/non-interactive-mode).

## Подготовка на сервере

После копирования файлов нового выпуска в `/opt/ai-teacher`:

```sh
cd /opt/ai-teacher
bash setup-authoring.sh
```

Скрипт создаёт закрытые каталоги `author-jobs`, `codex-auth`, новый worker-токен без вывода значения и `authoring.env` с GID Docker socket. Существующий токен сохраняется. Каталоги заданий и авторизации принадлежат UID/GID 1000; брокер работает под этим пользователем с дополнительной группой Docker socket.

Применяются оба Compose-файла:

```sh
docker compose --env-file release.env --env-file authoring.env \
  -f compose.production.yaml -f compose.authoring.yaml \
  build author-image render-image author-broker
```

## Отдельный вход Codex

Сначала соберите образ автора. В доверенной серверной консоли выполните:

```sh
cd /opt/ai-teacher
. ./release.env
. ./authoring.env
docker run --rm -it --read-only --user 1000:1000 \
  --cap-drop ALL --security-opt no-new-privileges:true \
  --tmpfs /tmp:rw,nosuid,nodev,size=128m,mode=1777 \
  --mount "type=bind,src=${AI_TEACHER_CODEX_AUTH:-/opt/ai-teacher/codex-auth},dst=/codex" \
  -e CODEX_HOME=/codex \
  "routemotion-lesson-author:${AI_TEACHER_VERSION:-latest}" \
  codex login --device-auth
```

Откройте показанный официальный адрес и подтвердите показанный одноразовый код. Содержимое `auth.json` не нужно открывать, отправлять в чат или переносить с компьютера. Проверка отдельного входа без вызова модели:

```sh
docker run --rm --read-only --user 1000:1000 \
  --tmpfs /tmp:rw,nosuid,nodev,size=128m,mode=1777 \
  --mount "type=bind,src=${AI_TEACHER_CODEX_AUTH:-/opt/ai-teacher/codex-auth},dst=/codex" \
  -e CODEX_HOME=/codex \
  "routemotion-lesson-author:${AI_TEACHER_VERSION:-latest}" \
  node /runtime/author.mjs auth
```

Команда выводит только признак авторизации и её тип. Доступ к выбранной модели проверяется настоящим заданием; сам факт входа не гарантирует доступ к модели или квоту. Совместимость песочницы Codex с ядром/namespace целевого Docker-хоста также проверяется настоящим заданием. Не включайте привилегированный контейнер ради обхода такой ошибки.

## Смена аккаунта по запросу владельца

Для другого аккаунта выполняется новый `codex login --device-auth` в отдельном закрытом серверном каталоге. Пользователь сам входит в нужный аккаунт на официальной странице и подтверждает код; авторизация настольного приложения не переносится. После успешного входа проверяется только `configured/mode`, каталог получает UID1000 и права700, файл авторизации600. Только затем `AI_TEACHER_CODEX_AUTH` в `authoring.env` указывает на новый каталог. Брокер пересоздаётся при пустой очереди, прежний каталог остаётся закрытым для восстановления. Активные задания не перезапускаются ради смены аккаунта. Содержимое файлов авторизации не читается и не включается в исходный архив или копию университетской базы.

22 октября владелец подтвердил отдельный вход нового аккаунта для routemotion.uz. Настройка `AI_TEACHER_CODEX_AUTH` переключена на выбранный закрытый каталог после проверки входа; модель `gpt-6.1-sol` / `ultra` и готовая озвучка Flash 3.8 / Puck сохранены. Настоящее авторское ревью с этим аккаунтом завершилось успешно. Это подтверждает выполненный вызов модели, но не гарантирует будущую квоту. Процедура входа описана в [официальной документации OpenAI](https://learn.chatgpt.com/docs/auth#login-on-headless-devices).

## Запуск

```sh
docker compose --env-file release.env --env-file authoring.env \
  -f compose.production.yaml -f compose.authoring.yaml \
  up -d --no-build author-broker ai-teacher
```

Отсутствие входа Codex даёт `configured:false` у worker; работа сайта и просмотр готовых уроков сохраняются. Сеть worker, адрес и token-file основного приложения заданы в `compose.production.yaml`, поэтому обычное восстановление сайта после ежедневного копирования не удаляет интеграцию.

Брокер восстанавливает готовые задания с диска без повторных вызовов автора. Прерванные `queued/running` помечаются ошибкой; остаточные контейнеры удаляются только по собственным меткам и именам worker. Сценарий и первичная постановка ограничены 30 минутами, содержательное ревью — 45 минутами, проверка — 5 минутами, рендер — 90 минутами; общий двухчасовой срок имеет приоритет. Процесс Codex завершается немного раньше внешнего лимита. Если первичная постановка прервана после сохранения настоящего scene.js, брокер может продолжить только через новую проверку, обязательное авторское ревью, повторную проверку и полный рендер. Повтор failed/interrupted задания с тем же входом также переиспользует сохранённый проект; наличие файла никогда не означает ready.

`author-jobs/<sha256>/` содержит вход, записанную озвучку, код, кадры проверки и итоговый MP4. Приватный журнал и состояние брокера хранятся отдельно в `author-jobs/.broker-state/<sha256>/`. Эти каталоги не раздаются сайтом. Готовый результат сохраняется основным приложением в его постоянное хранилище. Автоматическая очистка рабочего каталога не включена; не удаляйте активные задания или единственный экземпляр готового результата. Авторизация Codex находится отдельно от регулярной копии базы.

## Внутренний протокол

Все запросы, включая `/health`, требуют `Authorization: Bearer <worker-token>`.

| Запрос | Результат |
| --- | --- |
| `GET /health` | `ok`, `configured`, `mode`, `busy`, размер очереди; секреты не возвращаются. |
| `POST /jobs/<64hex>/script` | JSON-контекст. `202` для очереди, `200` для уже готового задания. |
| `GET /jobs/<64hex>/script` | Состояние; готовый `result` — объект сценария. |
| `PUT /jobs/<64hex>/assets/<id>.wav` | WAV и `X-Content-SHA256`; 60 МБ на файл, 80 МБ на задание. Повтор готового файла с тем же хешем допускается. |
| `POST /jobs/<64hex>/visuals` | Главы с фактическими временами озвучки; запуск проверки и сборки. |
| `GET /jobs/<64hex>/visuals` | Состояние; `result` включает измеренные параметры видео и SHA256. |
| `GET /jobs/<64hex>/artifact` | Проверенный MP4 готового задания. |

Ошибка возвращает только код `AUTH`, `MODEL`, `RENDER`, `VALIDATION` или `BUSY` и короткое сообщение. Журнал команд остаётся в закрытом каталоге задания. Готовое задание идемпотентно и не запускается снова при повторе с тем же входом.

В адаптере основного приложения подготовлена каноническая сериализация запроса: ключи вложенных объектов сортируются, порядок массивов глав и реплик сохраняется. Для SHA256 задания и отправки используются одни байты, поэтому переупорядочивание ключей PostgreSQL JSONB не должно создавать другое задание. Локальная проверка прошла; адаптер включён в API-выпуск `20261022T094404Z`. Новый реальный вызов Codex при проверке API не запускался.

Локально проверены синтаксис, объединённая конфигурация Compose и протокол на изолированном имитаторе Docker. Полная контейнерная проверка требует работающего Docker на целевом сервере; локальный Docker daemon при подготовке был недоступен.

## Профили Linux для автора

На целевом Docker-хосте стандартный профиль не разрешил Bubblewrap создать namespace. Диагностические пробы отделили ограничения seccomp и AppArmor: одного изменения seccomp оказалось недостаточно. Для рабочего автора подготовлены отдельные `worker-seccomp.json` и AppArmor-профиль `routemotion-lesson-author`; `unconfined` не используется в конфигурации worker.

Исходники — [официальный seccomp Moby](https://github.com/moby/profiles/blob/4b8214fc4971e06172938a1f1554ccff6647ee80/seccomp/default.json) и [шаблон AppArmor Moby](https://github.com/moby/profiles/blob/4b8214fc4971e06172938a1f1554ccff6647ee80/apparmor/template.go), Apache-2.0. Точный commit и изменения записаны в `deploy/worker-security-sources.json`, лицензия сохранена рядом. Добавлены вызовы namespace/mount, необходимые Bubblewrap; остальной список разрешений/запретов Moby сохранён. AppArmor разрешает mount/pivot_root/userns внутри авторского контейнера, сохраняя ограничения `/proc`, `/sys` и устаревших семейств сокетов. Профиль рендера, основного сайта и других контейнеров не меняется.

`setup-authoring.sh` устанавливает только именованный профиль через `apparmor_parser`, не меняет sysctl хоста и не включает privileged. У автора остаются `cap-drop ALL`, `no-new-privileges`, корень только для чтения и отсутствие базы/Docker socket. Брокер читает seccomp-файл из `/run/security/worker-seccomp.json`; Docker CLI передаёт профиль демону. Профиль успешно разобран серверным apparmor_parser. После добавления отдельного разрешения pivot_root серверная проба песочницы прошла: запись в рабочий каталог разрешена, чтение /codex/auth.json запрещено. Запрет всего /codex мешал служебным helper aliases, поэтому политика автора закрывает конкретный файл авторизации, журналы и /run/secrets; ключи также исключены из окружения инструментов. Настоящие вызовы модели для сценария и 3D-проекта подтверждены пилотом; выпуск полного фильма ещё не подтверждён.

Состояния заданий, исходные снимки входа и приватные журналы находятся в `/jobs/.broker-state/<sha256>/`, за пределами каталога, монтируемого в автор/рендер. В `/job` передаётся только текущий `input.json`, озвучка и рабочие выходные файлы. Чтение готовых файлов проверяет `realpath`, чтобы символическая ссылка в проекте не вывела брокер за пределы одного задания.

Chromium сохраняет служебную конфигурацию и кеш в `XDG_CONFIG_HOME=/tmp/chromium-config` и `XDG_CACHE_HOME=/tmp/chromium-cache`; домашний каталог не переназначается. Это исправляет обнаруженный в контейнере отказ Crashpad на корневой файловой системе только для чтения. После изменения серверный Docker-рендер синтетического двухсекундного примера прошёл: два прохода кодирования, проверены видео- и аудиопотоки и 48 кадров. Контейнер работал без сети, с корнем только для чтения, UID 1000, ограничениями 4 ГБ / 2 CPU. Это проверка движка на коротком синтетическом примере, а не фильм, созданный Codex.

## Фактический объём проверки

На сервере подтверждены отдельный вход Codex (`configured:true`, `mode:chatgpt`), работа именованных профилей песочницы и короткий контейнерный рендер. Протокол брокера проверен отдельно на имитаторе Docker: авторизация запросов, WAV/SHA256, одна постановка при конкурирующих запросах, повторная загрузка готового WAV, повтор готового задания после перезапуска, закрытые ошибки, недоступность состояния брокера из рабочего проекта и запрет внешней символической ссылки.

История пилота, 21 октября: gpt-6.1-sol / ultra создал сценарий с проверенными математическими примерами. Первоначальные 1559 слов дали около 776 секунд озвучки; текст был сокращён до 1145 слов. Повторный проход Gemini 2.5 Pro TTS / Puck дошёл до 24 из 32 реплик и остановился на суточной квоте Google 50 запросов на проект/модель с RetryInfo 71282 секунды. Этот этап и его кэш сохранены; после прослушивания нового образца пользователь выбрал Flash 3.8 / Puck. Прежняя остановка не описывает текущее состояние озвучки.

Текущее состояние, 22 октября: индивидуальная 3D-постановка создана, настоящее авторское ревью с новым серверным аккаунтом прошло, обрезка делений осей исправлена. Исходный GLB автомобиля, PBR-материалы, код сцены и готовая озвучка не менялись ради ускорения рендера. После отмены полного рендера пользователем сохранён готовый экспорт первых 240 секунд / 5760 кадров с исходным голосом Puck. Полного нового десятиминутного MP4 нет; это задание не возобновляется.

Прежняя двухсекундная проверка (48 кадров за 14,2 с) описывает исходные ограничения 2 CPU / 4 ГБ. Код и Compose теперь имеют значение по умолчанию 6 CPU / 6 ГБ; для текущего production-выпуска выбран `WORKER_RENDER_CPUS=8`, память — 6 ГБ. Изоляция сети и файлов и ограничения автора сохранены. Рендер ограничен 90 минутами; общий двухчасовой срок задания имеет приоритет. Это лимиты, а не обещанное время готовности.

### Программный рендер Mesa

В новом образе выбран `WORKER_RENDER_DRIVER=llvmpipe`, `EGL_PLATFORM=surfaceless`, `LIBGL_ALWAYS_SOFTWARE=true`, `GALLIUM_DRIVER=llvmpipe`. Chromium работает через ANGLE/EGL; физический GPU не используется. Доверенный код проверяет фактический `glRenderer` через браузерный CDP `SystemInfo.getInfo` и отклоняет несовпадение, включая скрытый переход на SwiftShader. Проверка выполняется вне авторской страницы.

На неизменённой сцене проведён реальный короткий замер: 96 кадров / 4 секунды, `antialias:true`, `preserveDrawingBuffer:true`. Среднее время кадра с Mesa llvmpipe — около 267 мс, с SwiftShader — около 1076 мс. Четыре контрольных состояния приняты по качеству. Это измерение данного сервера и короткого участка, без экстраполяции на все 600 секунд. Образ Mesa уже развёрнут на сервере под существующим тегом `routemotion-lesson-render:20261021T124100Z`, digest `sha256:0982663255bd7baeef2b7b697ed01716a68bde8db07476819fcb6c03cf721e18`. Тег относится к уже установленному образу, а не к ожидаемой сборке. В нём прошёл синтетический аудио/видеопример 2 секунды / 48 кадров; свежая проверка настоящего проекта дала 38 прямых и 38 обратных контрольных кадров, визуально приняты все 38 состояний. Это не подтверждает полный десятиминутный MP4: его рендер отменён пользователем.

Финальный аудиопроход добавляет тихую детерминированную гармоническую подложку и короткие переходы по границам глав. Их создаёт доверенный `render.mjs` без внешних файлов, API и аудиокода автора. Среднечастотный EQ и sidechain освобождают место голосу; автоматическая нормализация выключена, задержка лимитера компенсируется. Двухпроходное кодирование и строгая проверка длительностей/кадров сохранены. Короткий фактический тест: `node worker/tests/audio-mix.mjs`; для проверки внутри образа можно смонтировать тест и задать `RENDER_MODULE=/runtime/render.mjs`. Результат локального двухсекундного теста описан в `VALIDATION.md`, полный фильм остаётся отдельной содержательной приёмкой.

## Квота Google TTS

После прослушивания реального образца пользователь выбрал Gemini 3.8 Flash TTS / Puck для новой полной озвучки. Код сохраняет профиль модели/голоса/языка/стиля; при смене пересчитывает WAV и тайминги, сохраняя исходный сценарий и прежний кэш. Начальный объём сценария учитывает модель, последующая подгонка опирается на измеренный полный голос. Пробные 28.24 секунды получены без ускорения. Финальный пилот: 8 глав, 1233 слова / 36 реплик, 569.84 секунды речи и 30.16 секунды пауз; собрано ровно 14 400 000 отсчётов PCM / 24 kHz, то есть 600 секунд. Начальный бюджет Flash откалиброван на 1200–1300 слов; дальнейшая подгонка использует реальный замер. Все WAV проверены на обрезания, клиппинг и длинную тишину; приблизительное ASR используется только как дополнительное свидетельство. Авторское ревью сцены завершено; полный новый MP4 не готов, его рендер отменён пользователем. Готовый четырёхминутный экспорт сохраняет исходный Puck.

Число запросов зависит от числа новых реплик: для нынешних 36 реплик без кэша потребовалось бы 36 первичных запросов. Подгонка длительности и повторы добавляют запросы; неизменённые фрагменты переиспользуются по точному хешу текста и профиля голоса. Новый ключ того же проекта не увеличивает его квоту.

Для устойчивой генерации нужна достаточная квота конкретного проекта и модели. Проверьте billing и активный Tier в AI Studio; если проект уже платный, запросите увеличение лимита, одобрение не гарантировано. Сам ответ с лимитом 50 не доказывает отсутствие billing. Суточная квота сбрасывается в полночь Pacific; время продолжения сверяется с RetryInfo. См. [лимиты Google](https://ai.google.dev/gemini-api/docs/rate-limits) и [проверку billing/Tier](https://ai.google.dev/gemini-api/docs/billing).

## Отменённый полный пилот и сохранённый экспорт

Полный 600-секундный рендер отменён пользователем; автоматическое продолжение не планируется. Сохранённый MP4 первых четырёх минут содержит 240 секунд / 5760 кадров и исходный голос Puck. Он не выдаётся за готовый десятиминутный урок. [Таблица проверки полного пилота](VALIDATION.md#полный-600-секундный-пилот--отменён) сохраняет неполученные подтверждения явно. Исторический встроенный V3 длительностью 640.064 секунды и семь записей его просмотра на 21–27 октября сохранены.

## API внешних платформ

Публичный `/api/v1` относится к основному приложению и использует тот же существующий конвейер генерации. Он не открывает внутренний брокер или Docker и не запускает заново отменённый пилот. Отдельное подключение создаёт администратор в `/admin/integrations`; серверные API-ключи и HMAC-секрет Webhook показываются один раз. Worker-токен остаётся отдельным внутренним секретом.

Контракт и примеры: [INTEGRATION-API.md](INTEGRATION-API.md), [публичная документация](https://routemotion.uz/api/v1/docs), [OpenAPI](https://routemotion.uz/api/v1/openapi.json).
